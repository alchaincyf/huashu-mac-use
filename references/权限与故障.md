# 权限与故障排查

**什么时候读这份**：操作发出去了但没效果、截图是空的或报错、AX 树返回 0 个窗口、
osascript 报了一串负数错误码、要引导用户去授权、或者怀疑是环境（代理/锁屏/Space）在捣鬼。

⚠️ **保质期不一样**：错误码和 TCC 的行为逻辑耐用；**系统设置的面板名和
`x-apple.systempreferences:` 深链接易腐**（Apple 改过多次）。
引导用户之前先自己跑一次那条 `open`，确认真的打开了对应面板，没打开就把这份文件改对。
本文里带具体 macOS 版本号的结论同理，换了大版本要复核。

## 一、TCC 是五种独立的 service，不是三种

| 你要做的操作 | TCC service | 系统设置里的位置 |
|---|---|---|
| `screencapture` / 截窗口 / **读窗口标题** | `kTCCServiceScreenCapture` | 录屏与系统录音（macOS 26 改的名） |
| `CGEventPost` / `CGEventPostToPid`（合成键鼠） | `kTCCServicePostEvent` | 辅助功能（与下一项合并显示） |
| `AXUIElement` 读写别的进程 | `kTCCServiceAccessibility` | 辅助功能 |
| `CGEventTap` 监听 | `kTCCServiceListenEvent` | **输入监控（独立一项）** |
| `tell application "X"` | `kTCCServiceAppleEvents` | 自动化（按「源→目标」二元组逐个授权） |

两条容易漏的：

- `System Events` 的 `keystroke` 要**同时**过两关：你的终端 → System Events 的自动化授权，
  **以及 System Events 自己**的辅助功能授权。这是「我机器上能跑、换台机器静默失败」的头号原因。
- 辅助功能是输入监控的**单向超集**：有辅助功能自动有输入监控；反过来只有输入监控时
  `AXIsProcessTrusted()` 返回 false。

## 二、🔴 权限归因到「责任进程」，也就是用户正在用的终端 app

同一个二进制、同一路径、同一签名，唯一变量是责任链，结果就完全相反：

```
正常运行（责任进程 = FanBox.app）：ScreenCapture=true   AXTrusted=true
断开责任链                        ：ScreenCapture=false  AXTrusted=false
```

对引导文案的直接含义：

1. 必须说「请授权**你正在用的终端 app**」（Terminal / iTerm / Cursor / FanBox），
   **不是「授权这个脚本」。换个终端要重新授权。**
2. `.sh` / `.py` / `.scpt` **永远不会**出现在授权列表里——它们不是可执行的签名主体。
   给 `node` / `claude` 这类二进制单独授权在这条链路上是无效动作。
3. 重置权限要对着终端 app 的 bundle id：`tccutil reset ScreenCapture com.huashu.fanbox`。
4. `tccutil` 只有 `reset SERVICE [BUNDLE_ID]` 一个可用用法，strings 里那个隐藏的 `check` 调用会被拒。
   别在这上面浪费时间。

## 三、预检：四个不弹窗的 API，两条反直觉行为

```c
CGPreflightScreenCaptureAccess()   // 只查不请
CGRequestScreenCaptureAccess()     // 会弹
CGPreflightPostEventAccess()       // 几乎无人知道
CGPreflightListenEventAccess()     // 几乎无人知道
```

1. **只调 preflight 的 app 永远不会出现在屏幕录制列表里**，会陷入「永远拿不到权限，
   因为从来没申请过」的死循环。启动时必须调一次 `CGRequestScreenCaptureAccess()`。
2. **权限改了必须重启进程才生效。**进程生命周期内 preflight 的返回值不会变，
   在定时器里轮询它是白费的。

纯 shell 的轻量预检（实测可用）：

```bash
osascript -e 'tell application "System Events" to get name of first process whose frontmost is true' \
  || echo "辅助功能/自动化缺失"
screencapture -x "${TMPDIR}_probe.png" || echo "屏幕录制缺失"
```

自动化的零弹窗预检走 `AEDeterminePermissionToAutomateTarget(..., askUserIfNeeded: false)`：
`0` 已授权 / `-1744` 还没问过 / `-1743` 被拒 / `-600` 目标没运行测不出来。
**目标没运行时无法预检**，得先把它拉起来——好在 `activate` / `open` / `open location` / `quit`
是 Apple 明确豁免、不需要自动化权限的操作。

引导用的深链接（macOS 26.3.1 实测三个都有效）：

```bash
open "x-apple.systempreferences:com.apple.preference.security?Privacy_ScreenCapture"
open "x-apple.systempreferences:com.apple.preference.security?Privacy_Accessibility"
open "x-apple.systempreferences:com.apple.preference.security?Privacy_Automation"
```

## 四、错误码对照

| 现象 | 码 | 含义 |
|---|---|---|
| osascript 报「不允许辅助访问」 | **-1728** | 没有辅助功能 |
| AppleScript 自动化被拒 | **-1743** | errAEEventNotPermitted，去自动化面板 |
| AppleEvent 超时 | **-1712** | 目标可能卡在模态 sheet。**重试前先确认上一次是否已生效** |
| AppleEvent handler failed | **-10000** | 常见于前置条件不存在（比如没有 front document） |
| AX API 被禁 | **-25211** | ⚠️ **权限已授权时也会出现**，`click at` 这类命令自身的通病 |
| AX 元素失效 | **-25202** | 窗口重绘/列表滚动后旧引用作废。**重新从根节点查找**再重试 |
| AX 目标忙 | **-25204** | 可退避重试 |
| 属性不支持 | **-25205** | 结构性问题，别重试。豆包工作设 `AXManualAccessibility` 就是这个 |
| 动作不支持 / 未实现 | **-25206 / -25208** | 结构性问题，换路线 |
| ScreenCaptureKit 无权限 | **-3801** | |
| System Events 拿不到窗口 | **-1719 或静默返回空列表** | 空列表不等于没窗口，见下 |

**分类重试**：`-25204`、`-25202`（重找元素后）、`-1712`（确认幂等后）可以重试；
`-25205` / `-25206` / `-25208` / `-25211` / `-1743` 一律不重试——那是结构性或权限问题，
重试只是浪费往返。

## 五、三种「静默返回空」，不是报错，最容易误判

1. **权限刚勾上，第一次调用返回空列表。**别当成「这个 app 没有窗口」，等几秒重试。
2. **AX 窗口枚举受 Space 限制。**同一时刻三个数据源三个答案：`CGWindowList` 报 1 个窗口 ✅、
   app 自己的 AppleScript 字典报 1 个 ✅、**AX 与 System Events 报 0 个** ❌。
   对照实验证明原因是 Space 而非「AX 只能看前台」（Finder 在后台时 AX 窗口数是 1）：
   **AX 窗口数严格跟随 `kCGWindowIsOnscreen`，两个信号完美反相关。**

   > 现实后果很严重：**agent 跑在一个全屏的终端里（很多人就是这么用）时，
   > 用户在普通桌面上打开的所有窗口，AX 查询全部返回 0**，会得出「这个 app 没有窗口」的
   > 错误结论并走进完全错误的分支。

   便宜的判据与防御顺序：
   ```
   目标窗口 onscreen=false 且 自己的终端窗口 onscreen=true ⇒ 不在同一 Space ⇒ AX 必返 0，别浪费往返
   1. 用 CGWindowList 判窗口存在性（跨 Space 可靠，权威判据）
   2. 存在 → 才试 AX 读结构
   3. AX 返 0 但 CGWindowList 有 → 在别的 Space：
        读取任务 → mac shot <id>，不切 Space
        操作任务 → 必须 activate，接受 Space 切换
   ```

   🔴 **但「activate 就会切 Space」是错的，这条我 2026-09-01 实测证伪了。**
   agent 跑在全屏的 FanBox 里、豆包工作在另一个普通桌面时：
   `open -a /Applications/DoubaoWork.app` 之后 `mac frontmost` **确实回「豆包工作」**，
   看起来激活成功了——但 Space **没有切**，屏幕上仍然是全屏的 FanBox。
   随后 `mac clickin` 报 `clicked (256,243)`，**事件打在了 FanBox 上**，
   紧接着 `mac frontmost` 变回 FanBox。连试三次，目标窗口截图差异恒为 `None`。

   **合成点击是打给「当前 Space 上那个位置的窗口」的，不是打给 frontmost app 的。**
   所以跨 Space 时点击不是无效，是**打错了对象**——比无效危险，它会去戳用户正在用的窗口。

   判据（一条命令，做任何写操作之前先跑）：

   ```bash
   screencapture -x -o /tmp/space.png   # 全屏截一张，看当前 Space 上到底是谁
   ```

   `mac frontmost` 回目标名 **不能**作为「可以开始点了」的凭证；
   全屏截图里看见目标窗口才是。两者不一致就是跨 Space。

   跨 Space 的唯一出路是**请用户把两个窗口放到同一个 Space**
   （终端退出全屏，或把目标窗口拖过来）。切 Space 要靠 Mission Control 快捷键，
   那会打断用户正在做的事，属于第七节的停手线，**不要自己动手切**。

   `# 核对 2026-09-01`
3. **无屏幕录制权限时 `CGWindowListCopyWindowInfo` 照常返回列表，但 `kCGWindowName` 全为空。**
   窗口标题本身受屏幕录制权限管辖。另外 `kCGWindowIsOnscreen` 是**缺席而非 false**
   （Swift 里读到 nil）；`kCGWindowName` 有三态：有标题 / 空串 / 完全缺席，空串不等于没窗口。

## 六、截图被拒的两种表现，都要处理

- A：仍产出文件、退出码 0，但只有壁纸和窗口边框（流传最广的说法）
- B：报 `could not create image from display`、exit 1、不生成文件（本轮独立实测到的）

推断差别在于是「从未授权」还是「被显式拒绝或 reset 过」。所以校验要既看退出码也看内容：

```bash
mac shot "$WID" out.png || { echo "截图失败（权限/窗口未渲染/已锁屏）"; exit 1; }
# 判据用相对比较，不要用绝对阈值：小窗口、纯文本界面正常就可能只有十几 KB
new=$(stat -f%z out.png); old=$(stat -f%z before.png 2>/dev/null || echo 0)
[ "$old" -gt 0 ] && [ $((new * 5)) -lt "$old" ] \
  && echo "警告：比同窗口的 before 小了 5 倍以上（${new}B vs ${old}B），疑似权限降级或空白窗口"
```
没有 before 可比时，就直接看图里有没有该有的非壁纸内容，别靠体积猜。
量级参考（**实测机器 1512×982、换机器要重测**）：全屏 PNG 约 881KB、JPEG 约 667KB；
纯壁纸图小一个数量级。

**「不报错但内容是空的」是最危险的失败模式**——退出码 0，脚本继续跑，模型看着一张壁纸开始瞎猜。

## 七、无人值守的两堵硬墙，无技术手段可绕

1. **屏幕录制权限会周期性重新确认。**macOS 15 起截屏类 app 有周期性弹窗（现为每月，
   文案「Allow For One Month」），用户和开发者都关不掉。唯一豁免的 entitlement
   （`com.apple.developer.persistent-content-capture`）Apple 定位为 VNC 专用，个人拿不到。
   **所以要把「截图返回异常」当成正常分支处理，不能 assert。长期无人值守的截图自动化
   在这条上一定会周期性断掉。**
2. **MDM/PPPC 不能静默授予屏幕录制和输入监控。**（网上大量二手文章包括 MDM 厂商 blog
   都说能，那是错的。一手文档原文：`silent allow is not supported`。）
   辅助功能和 AppleEvents 可以静默授予，屏幕录制和输入监控不行。

## 八、非 GUI 会话

锁屏本身是关卡，判据与解法见 SKILL.md 第七节的「🔴 STOP · 锁屏」，这里只补两条实现细节：

- **剪贴板和截屏一样绑定 Aqua GUI session。**作为后台服务运行时，即使权限全给了，
  `NSPasteboard.generalPasteboard` 也会返回 nil。
- 所以：**别假设脚本能在 launchd / ssh / 定时任务里跑。**做定时任务类工作时这是头号坑。
- ssh 场景下唯一的解是挂进 loginwindow 的 mach bootstrap 层级
  （`sudo launchctl bsexec $(pgrep -x loginwindow) screencapture ...`），代价是要 sudo。

## 九、环境坑

- 🔴 **机器上跑着 Clash 之类的本地代理时**，`curl` 本机端口不加 `--noproxy "*"` 会被代理吞掉，
  误判成「这个 app 没开本地服务」。本轮因此差点漏掉两个 app 的调试端口。
  **这是全 skill 唯一一处解释这个参数的地方**，别的文件只保留参数本身。
- **Clash 必须 rule 模式**：global 模式下部分国内域名被推去国外节点，全线 502
  （用户 WorkBuddy 手册已记录）。
- ⚠️ **macOS 上没有 `timeout` 命令**。`gtimeout` 要 `brew install coreutils`
  （实测机器 2026-08-30 未装），所以默认走纯 shell 后台 kill，别假设 `gtimeout` 在。
- **`TCC.db` 在 macOS 26 + SIP 开启下读不了**（用户库和系统库都 authorization denied），
  网上「查 TCC.db」的教程在一般用户环境不可用。可用的排查是看归因链：
  ```bash
  # 裸跑没用，TCC 日志默认 <private> 遮蔽
  log stream --debug --predicate 'subsystem == "com.apple.TCC" AND eventMessage BEGINSWITH "AttributionChain"'
  ```
- **别自己编译 helper 二进制去请求屏幕录制。**macOS 26.1 有个 Apple 已确认的 bug：
  非 .app bundle 的裸可执行文件请求屏幕录制后不再出现在设置列表里，弹窗照弹、
  授权后照样能截图，但用户无法管理。所以内核 `mac shot` 是去调系统自带的
  `/usr/sbin/screencapture` 子进程（走责任进程归因，绕开该 bug），而不是自己调 CG API。

## 十、不打扰用户的四道闸（2026-09-03 加，对齐官方 computer use）

Anthropic 2026-09 放出的 computer use 把「Claude 在干活」和「你在用电脑」隔开，靠的不是更强的
操控，是四道闸：后台 app 作用域为默认；**每个动作前检查前台 app 是不是授权的那个，不是就报错
且什么都不做**；`generally waits if you're in the middle of typing`；藏无关 app 而不是激活目标，
且终端窗口排除在截图外。配套是机器级单会话锁、Esc 全局中断（按键被消费掉，防注入拿它关弹窗）、
敏感 app 只警告不阻止（终端 = 等同 shell 访问，Finder = 可读写任何文件）。

内核对齐了其中四条，全部在 `--dry` 里可预演（`闸预检:` 那一行）：

| 闸 | 拦什么 | 覆盖命令 |
|---|---|---|
| frontmost | 前台不是目标进程就拒绝 | `key` / `type ... global` / `click`（全局坐标看落点上层 pid） |
| 遮挡 | 落点最上层不是目标窗口就拒绝 | `clickin` / `hoverin` / `click` |
| 在场 | 用户 2 秒内动过键鼠 → 静等他停手，最多 15 秒，等不到拒绝 | 所有走全局流的写 + 所有借焦点档 |
| 借焦点锁 | 全机同时只允许一个进程借焦点，持有者退出自动失效 | `op` 借焦点档 / `shotfg` |

`--force` 拆全部闸。走 postToPid 的路径（`op --bg`、不带 global 的 `type`）直投进程、不碰前台，
本来就不打扰用户，因此不设闸。

### 三个非踩不可知的实现细节

**自己合成的事件会刷新系统空闲计时器。** 实测 post 一个 mouseMoved，`secondsSinceLastEventType`
从 165.7 秒掉回 1.0。不处理的话第一条命令的尾迹会让第二条命令误判「用户在动」而自锁，整套写操作
全部瘫痪。解法是把最后一次合成的时刻写进尾迹文件，读数与它吻合（差 <0.8 秒）就当自己的痕迹排除，
两路信号（keyDown / mouseMoved）分别判定。keyDown 那一路只有走 global 才会被自己污染。

**`mac key` / `type ... global` 打给「当前前台窗口」，pid 参数只用于回显。** 前台随时会被用户切走，
所以 pid 传对了不等于打对了地方。2026-09-03 实测踩中两次：一次前台已从 FanBox 变成 Chrome，回车
按进了浏览器；一次前台是微信，`key 36` 直接按在聊天窗口上。frontmost 闸就是为这个加的。

**`--dry` 必须走完闸再退出，否则没法安全预演。** 旧版 `--dry` 只解析坐标就 exit，闸在它后面，
于是「这一下会不会被拦」只能拿真命令去试——而条件不满足时它就真执行了。上面两次误操作正是这么
来的。现在 `--dry` 零执行但报出每道闸的判定，测试拒绝分支一律用它。

### 在「agent 跑在全屏终端里」的拓扑下，遮挡闸几乎轮不到

agent 跑在全屏 FanBox 里，那个 Space 只有 FanBox 一个窗口，别的窗口一律 `on=0`，cross-space 闸
先于遮挡闸触发。遮挡闸是为非全屏拓扑准备的。（2026-09-03 实测：拒绝分支在用户切到 Chrome 时
被真实触发过一次，放行分支在 `hoverin` 目标即最上层时验证。）

### 接管屏幕时的 HUD：三条约束缺一条它自己就成了干扰源

借焦点那一两秒，用户看到的是窗口自己跳到前面、光标自己动——不解释就是「见鬼了」。官方只发一条系统
通知，内核做得更直观：屏幕四角脉冲一圈取景框 + 一行说明（`mac hud`，借焦点时自动闪）。

| 约束 | 实现 | 破了会怎样 |
|---|---|---|
| 鼠标穿透 | `ignoresMouseEvents = true` | 提示自己挡住用户所有点击 |
| 永不抢焦点 | `.accessory` 激活策略 + `nonactivatingPanel` + `orderFrontRegardless()`（**不是** `makeKeyAndOrderFront`） | 为了提示「我要抢焦点了」而先抢了焦点 |
| 跨 Space 常驻 | `[.canJoinAllSpaces, .stationary, .fullScreenAuxiliary]` | 用户切一下 Space 提示就没了 |
| **对屏幕捕获隐身** | `sharingType = .none` | **每张取证截图都带着橙边框和标签，整批图作废** |

最后一条是用户提的，也是最容易漏的：这个 skill 的核心交付是可复现的取证截图，提示框进了图就等于
图废了。`sharingType = .none` 让窗口对人眼可见、对任何捕获不可见，实测全屏 `screencapture` 在 HUD
显示期间截出来完全干净，不需要任何时序协调。要录屏演示这个功能本身时用 `MAC_HUD_CAPTURABLE=1`。

样式三选：`corner`（默认，四角 L 形取景框，中间全空不压内容）/ `glow`（粗边框+内侧辉光，最醒目）/
`plain`（细边框）。2026-09-03 用户看过三张全屏真图后选的 corner。
