# 取证规范——截图怎么命名、放哪、怎么合规、怎么能重跑

**什么时候读这份**：截图要进用户的实测项目、要给一批截图命名归位、要判断某张图能不能上图床、
要组织多模型同题跑批、或者要把「一键重跑重截」做成可重放的东西。

规范全部来自用户已经在做的事（`<写作项目>/` 下五个实测项目），
**照抄，不要重新发明**。

---

## 一、三套命名规范，按「这张图给谁看」分

三套并存，各有明确适用场景，**不能混用**。

| 套 | 格式 | 用在哪 | 谁产出 |
|---|---|---|---|
| **A 正文配图** | `配图/NN-中文描述.jpg`，NN 是**正文出场顺序** | 已选定要进文章的成品图 | 目前纯人工 |
| **B 实测物证** | `视觉/<题>/<题>-<模型>-<NN><时刻名>.png` | 跑批产出的定点截图 | 脚本自动 |
| **C 原始素材** | `素材/界面NN-描述-日期.png`，或 macOS 默认的 `截屏YYYY-MM-DD HH.MM.SS.png` | 手截的界面、客户发来的图、官方素材 | 目前纯人工 |

实例：`06-改造完成报告.jpg`、`14-44个图标总览.jpg`（A 套）；
`<题>-<模型A>-04俯视地形.png`、`<题>-<模型B>-04俯视地形.png`（B 套，注意时刻名逐字相同）；
`界面05-权限三档-20260812.png`（C 套）。

🔴 **B 套的时刻名跨模型逐字一致是硬依赖，不是习惯。**拼图脚本直接按
`f'{题}-{模型}-{时刻}.png'` 拼四宫格，命名错一个字就拼不出来。
本 skill 做定点截图时**必须先要到（题 / 模型 / 时刻名）三元组再动手**，
时刻名从第一个模型的那次跑批里抄，不许自己另起。

**截图不落桌面，直接落项目目录。**

## 二、目录落位（每个项目结构一致）

```
项目/<年月>-<客户>实测项目/
  素材/                       原始未加工：手截原图、客户给的、手机发来的
  配图/                       正文成品（压过/拼过/标注过）
  配图/_原图/                 成品对应的未压 PNG
  配图/_已上传/               已传图床的那批
  实测-YYYYMMDD/视觉/<题>/     自动化截图 + 录屏 + console 日志（同名族）
  实测-YYYYMMDD/结果/<题>-<模型>/  产物 + transcript.jsonl + 会话全文.md
  _archive/                   弃用件
```

🔴 **`_archive/` 只 `mv` 不 `rm`。**这是用户铁律，本 skill 任何涉及清理的地方都遵守。
理由不只是洁癖：2026-08-19 客户推翻了打码判据（「Claude Code、Codex 这类国外产品名可以露出」），
旧成品图直接进 `_archive/06-改造完成报告-已打码-20260819前版本.jpg`，从原图重出一版。
**判据会被推翻，所以原图必须永远留着。**

## 三、尺寸、格式、压缩

- **正文图：JPG、长边 1600（实际 1400–2400 都出现过）、单张 <500KB。**这是 ImgBB 上传要求。
- **PNG 只在两处留**：自动化截图原件、自制信息图。发布前一律转 JPG。
- 压缩调现成的，不要现写 sips 循环
  （路径按 skill 实体目录写，不要写软链）：
  ```bash
  uv run <image-compress skill>/scripts/compress.py <图> --target 0.5
  uv run <image-compress skill>/scripts/compress.py --dir <目录> --target 0.5
  ```
  它已经做了二分搜索质量 + 多档兜底。（该 skill 明说 macOS 上 xargs 不可靠，别自己并发。）
- 🔴 **截产物时视口必须对齐产物的设计尺寸。**deck 是 1920×1080、信息图是 1080×1440。
  > 用户原话：「这套 deck 是 1920×1080 设计的，我一开始用 1600×900 截，右侧和底部内容被切掉，
  > 看起来像排版出错——差点把我自己的截图参数写成模型的排版缺陷。」
- **本 skill 的边界停在「图产出并归位、压到 <500KB」**。
  往下的发布动作（传图床换 URL、渡到排版器、GIF 在各平台的限制）交棒 image-generation 和 dukou，
  不在这里复述。

## 四、🔴 合规裁剪与打码

这是本 skill 最独特、也最容易出事的一条：**有些像素不能出现在图里，出现了就是客户事故。**

**禁像素清单**（从实际弃用理由归纳的**类别**）：
1. 保密期内的未发布模型名与内部代号 —— `<客户内部代号>`
2. 未公开的参数规模 —— `<未公开参数规模>`
3. 友商产品名
4. `$XXX_HOME` 一类本地路径
5. 侧栏里的无关项目名、顶部的另一个任务
   （真实弃用理由：「侧栏露出十几个无关项目名，且顶部是另一个任务」）

🔴 **具体的禁词真值一律不写进本 skill**，本 skill 会被多个 agent 共读并开源，
把客户代号写进来，这份文件本身就成了它要挡的那类载体。
**真值放在实测项目根目录的 `禁词.txt` 里，动手前读那个文件。**

**三条执行规则**：

- **界面截图一律不露模型下拉列表**（裁掉或让打码区避开）。**录屏同样要检查模型名露出。**
  **首图宁可不用界面图**，用产物拼图。
- **上传闸**：标注里带未发布代号的图，传到公开图床等于提前放出去。**没过合规扫描不许上传。**
  扫描要 OCR 时**复用 disk-keeper 的本地 Vision 管线**（`<disk-keeper 索引目录>/`，不联网不花钱），
  本 skill 只负责读禁词表和做拦截判断，不重造一套识别。
- **加工件与原图强制分离**：打码/裁剪的成品放 `配图/`，未打码原图留在 `素材/`，
  加工链可撤销、可重放。撤销时是**从原图重跑加工链，不是改成品图**。

**打码/高亮的坐标要写进文件、可复算**，并在文件头写明批注出处和日期。
实测项目里已有现成的打码脚本，照它的写法：文件头一句话记「按客户 YYYY-MM-DD 批注（做什么）」，
坐标块连同原图尺寸一起写死在常量里（`BLOCKS = [(左,上,右,下), …]  # 目测标定（原图 W×H）`），
**该留作对照的区域故意不高亮**——高亮全图等于没高亮。

⚠️ `sips -c <高> <宽> --cropOffset <上> <左>` 的参数顺序与直觉（宽高、左上）**相反**。

## 五、多模型同题跑批

🔴 **先明确目的**：跑多个模型是为了**留选择空间**（文章最终放哪几个，由用户挑），
**不是为了排座次**。红线原文：「这个品类的产品，将来大概率都是客户。不做横向对比评测。」
**对比表和排名不是默认产出物**，除非用户明确要。友商模型的跑批留作内部参考，不进文章。

已成型的四件机制，照抄：

**1. 跑批台账**（`实测-YYYYMMDD/跑批台账.md`）
> 每一跑的凭据在这。**引用任何实测结论前先查这张表它是不是有效跑。**

分「有效跑 / 作废跑」两张表，每行：题、模型、session id、起跑时间、状态、凭据。
作废原因要写到能复盘（真实的一条：「19:48 误提交：以为在跑赛车题，实际提交的是编辑器里
残留的 Excel 题面（210 字）。污染源就是它」）。

**2. 题面逐字闸门**——公平性靠它保证：
```python
'''提交物证(jsonl 的 user_query)必须与题面逐字一致，否则标作废'''
raise SystemExit(f'❌ session {sid} transcript 题面与文件不一致——已作废，勿用其结果')
```
🔴 **比对的不是你发出去的字符串，是回读 transcript 的 `user_query`。**
因为编辑器 DOM 和实际提交会不一致（WorkBuddy 的 Slate 编辑器实测 DOM 显示 344 字、
实际提交 210 字）。这跟第三节的「写完必须读回」是同一条纪律。

**3. 夹具清场**——每跑前把共享目录清空到只剩原始输入：
除原始文件外全部 **`mv`** 进 `_起跑前残留/<夹具>-$(date +%H%M%S)`（**不删，可追溯**），
再用 `md5 -q` 校验原始文件哈希没变。不清场的后果是下一个模型直接捡上一个的答案。

**4. 定点截图必须同一组动作**——「四个模型的产物必须用同一组参数、同一段操作跑，
否则对比不成立」。所以定点截图要做成**可重放的动作序列**，不是每次手点。

## 六、产物落点定位

> 「**产物落点不固定**：模型可能写进 session 自己的 cwd，也可能写进题面里点名的共享目录。」
> 「会话目录名是 `new-chat-1` 这种自动名，**找产物要靠搜索不靠记忆**。」

一次真实的素材盘点扫出 130+ 个文件，散在三处：项目 `素材/`、
`<app 会话目录>/2026-08-13/new-chat-1/...`、另一个 iOS 项目的隐藏目录。

**做法**：起跑前打时间戳 → 跑完按 mtime 扫落点白名单（`<app 会话目录>/`、
题面里点名的目录、session 的 cwd）→ 列出新增文件让用户确认 → 归档进
`实测-<日期>/结果/<题>-<模型>/` 并写回台账。找旧文件对接 **disk-keeper**（它有 OCR 索引），
不要重造索引能力。

## 七、重跑重截的硬约束

「**如果上线晚于发文日，全部界面截图都不能用，整篇的视觉素材要重做**」是随时会发生的事，
所以定点截图的动作序列要能重放，且三种重放场景都必须成立：
禁词解禁后原样重截；产品正式上线后改一个变量重跑；
客户推翻打码判据后**从原图重跑加工链**（不是改成品图）。

🔴 **锁屏是这里的硬约束，必须正面处理。**屏幕锁定时接口层操控照常、`screencapture` 直接失败——
**agent 能通宵跑批，却截不了图**。两条正当解法：提前唤醒 + `caffeinate` 防锁；
或把该步标成「需人在场」，解锁后批量补截。**不能假装能截。**

---

## 八、采集期不许丢指标

采集期的口径要比发布期宽——**报数口径随客户变**（这一家要耗时和工具调用次数、不要 token 和费用；
另一家正文里三个都不出现）。所以**实测阶段全记，发布阶段再筛，
本 skill 不能在采集期就丢弃指标**。

实测结论怎么组织进文章（判分口径、图注写法、图片密度），以 `<写作库>/` 的流程为准，
本 skill 不在这里另立一套。唯一要在这边守住的是第五节那条红线：
**跨模型并列表和排名不是默认产出，要用户明确点头才做。**
