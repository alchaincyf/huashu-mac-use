# 四层控制面详解

**什么时候读这份**：probe.sh 探出了一个本地端口不知道怎么用、AX 写入失败要判断该不该退层、
要从截图上的坐标算出能点的坐标（Retina 换算）、不确定某条输入路径的失败该怎么归因、
或者要判断慢在哪一步。

---

## L0 结构接口——默认起点，成本最低

按「找得到的概率」排序去探：

**1. 本地监听端口（Electron 类最值钱的通道）**

```bash
lsof -nP -iTCP -sTCP:LISTEN -a -p <pid>
curl -s --noproxy "*" -m 3 "http://127.0.0.1:<port>/json/version"
```
返回里有 `webSocketDebuggerUrl` 或 `Browser` 就是 **CDP**——直接走 CDP，别碰坐标，
并照 huashu-chrome 的「网络层优先」心智做事（要数据读接口，别在界面上读数字）。
⚠️ **借的是 huashu-chrome 的心智，不是它的工具。**它的 MCP 连的是用户的真 Chrome、带登录态，
到不了 Electron 实例的调试端口。**Electron 的 CDP 自己用 `curl` / `websocat` 连**，
或用 `app档案.md` 里记的那套现成工具链。

没有 CDP 时试带参数重启：`open -a "<App>" --args --remote-debugging-port=9333`。
WorkBuddy 实测就是这样才有 CDP 的，默认启动时只有一个所有常见路径都 404 的 HTTP 服务。

不是 CDP 就试 JSON-RPC：
```bash
curl -s --noproxy "*" -m 3 -X POST "http://127.0.0.1:<port>" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}'
```
实测遇到过一个 JSON-RPC 2.0 服务：GET 返回 `Method not allowed`，
POST 返回 `-32003 Unauthorized`——**有认证，token 未挖到**。这条挖通了就是最优路线。
⚠️ **端口号不要抄档案里的，Electron 高位端口每次启动都可能变**，一律 `lsof` 现查。

🔴 `--noproxy "*"` 一个字都不能省，原因见 `权限与故障.md` 第九节。

**2. AppleScript / JXA 字典**

```bash
plutil -p "<App>.app/Contents/Info.plist" | grep -E "NSAppleScriptEnabled|OSAScriptingDefinition"
```
有字典是**可靠性最高**的一层——完全不碰事件系统、原子操作、不抢焦点、中文照样写：
```bash
osascript -e 'tell application "TextEdit" to make new document with properties {text:"hello 中文测试"}'
```
现实是只有 Apple 系（Finder / Mail / Safari / TextEdit / 备忘录 / Keynote）字典较全，
多数第三方没有。但即使没字典，`activate` / `open` / `open location` / `quit` 也一直可用，
且这四个是 Apple 明确豁免自动化授权的。

**3. URL scheme**

`probe.sh` 会从 `CFBundleURLTypes` 读出来。注册了不等于能用——豆包工作有 `doubaowork://`，
但二进制 strings 里搜不到路由格式，挖不动就别耗。

**4. app 自己的配置文件 / 数据库**

有些状态直接读文件比操控界面便宜得多。**只读，不写**。

## L1 AX 语义树——探到可用才走

优势很实在：不经键盘、**不受输入法状态影响**（中文输入法开着也不会被拦截转换）、
一次调用写完整段（比逐字符快几十倍）、不需要键盘焦点、不动剪贴板、不抢前台。

### 唤醒顺序（`mac ax` / `mac axset` 已内置）

1. **只读一次目标 app 元素的 `AXRole`**——纯读，不可能有副作用。Chromium 和 Firefox 现在都
   在辅助技术读取 role 时自动打开 a11y。这是最通用的唤醒方式。
2. 树仍为空且确是 **Electron**，才退回设 `AXManualAccessibility`。
   这是 Electron 专属属性（**Chrome 从来不支持，Chromium 源码里根本没这个字符串**），
   Electron 不把它转发给 AppKit，所以没有窗口副作用。
   **设完必须轮询，不能设完就查**——实测设 true 后 0.5 秒重查仍是 0 个窗口，稍后同会话变成 2 个。
3. 🔴 **永远不要设 `AXEnhancedUserInterface`。**Mozilla 的 bug 标题直接叫
   「AXEnhancedUserInterface breaks window managers」，Spectacle 和 Magnet 都因此位置错乱；
   yabai 和 Rectangle 的做法都是临时关掉再恢复。反向风险更大：VoiceOver 正在运行时把它设 false，
   等于在活的屏幕阅读器用户脚下拆 a11y 树。
   （另：Chromium 给它加了 2 秒防抖，设完立刻读 `AXWindows` 会得出「没用」的错误结论。）

### 判据：三种结果三种走法

| `mac ax` 输出 | 含义 | 怎么走 |
|---|---|---|
| 可编辑控件 = 0 | 树是空的或断在 `AXWebArea` | 直接 L2，别在 AX 上耗 |
| 可编辑控件 ≥ 1，`mac axset` 读回是写入的内容 | 真通 | **最优路线，完全后台** |
| 可编辑控件 ≥ 1，`mac axset` 返回 `err=0` 但读回是空 | 🔴 **暗拒** | 老实退 L2 |

暗拒的成因推断：自绘控件、或依赖 `textDidChange` 的 Web/Electron 输入框，写入后 app 内部状态
不更新——文字出现了，但「搜索」按钮仍是灰的、React state 没变。
**所以 setValue 之后除了读回文字，还要看依赖控件是否变可用**（`get enabled of button "搜索"`
从 false 变 true 才算真生效）。

便宜的先验判据：`[ -d "<App>.app/Contents/Frameworks" ]` 有 → Electron/Chromium，AX 大概率能用；
没有 → 原生或自绘/WKWebView，树大概率是空的。粗略分布：原生 AppKit/Catalyst 完整；
SwiftUI 大体完整但层级深、role 泛化；Electron 默认关闭；裸 WKWebView / 自绘 Canvas / Java / Qt /
游戏引擎基本为空。

### 点击用 AXPress，不用坐标

凡是 AX 树里找得到的按钮，`AXUIElementPerformAction(el, kAXPressAction)` 都是「点击」的正解：
不移动鼠标、不需要窗口在前台、不受遮挡影响、不需要坐标换算。
局限是 web view 上可能返回 success 却什么都没做——照样要回读。

⚠️ **别依赖固定索引路径。**`text area 1 of scroll area 1 of window 1` 在 app 小版本更新后就断。
按 **role + title/description 匹配**遍历，找不到就报错而不是猜。
⚠️ **别缓存 AX 元素引用跨重试使用**，`-25202` 之后必须从根节点重新查找。

## L2 窗口坐标——AX 不可用时的主力

```bash
mac windows 千问                       # 拿 id / pid / origin / 尺寸
mac shot <id> /tmp/now.png             # 先拍一张，从图上定位控件
mac clickin <id> <窗口内x> <窗口内y>     # 自动加 origin
```

**用 `clickin` 传窗口内相对坐标，不要缓存全局坐标**——窗口会被拖动。
但 `activate` 之后窗口可能还在动画中，此时读到的 origin 是中间值，要等窗口稳定。

### 🔴 三套坐标系，Retina 上最容易错的地方

以一台逻辑 1512×982、物理 3024×1964（2 倍）的 Retina 机器为例：

| 坐标系 | 示例数值 | 谁在用 |
|---|---|---|
| 逻辑点 | 1512×982 | `CGEvent` 点击、`CGWindowBounds`、`mac click/clickin` 的入参 |
| 物理像素 | 3024×1964 | `screencapture` 出的图 |
| 我看到的图 | 被降采样（比如 2000 宽） | 我读图时用的坐标 |

换算链（从图上坐标 → 能点的坐标）：
```
窗口内逻辑坐标 = 图上坐标 × 窗口逻辑宽 / 图显示宽
全局逻辑坐标   = 窗口 origin + 窗口内逻辑坐标        # 用 clickin 就不用算这步
```
**演算示例用的是编出来的整数，只为演示这条乘法，任何真实 app 上都不成立**：
某窗口 origin=(100,100)、逻辑 1000×600，截图显示宽 2000（比例 1000/2000 = 0.5），
控件在图上 (600,400) → 窗口内 (300,200) → 全局 (400,300)。
🔴 **每一轮都要重新截图重新量**，窗口会移动、app 会改版。

四条坑：

1. **归一化的分母和乘回去的分子必须是同一个坐标系。**Open Interpreter 的经典 bug 就是
   分母用窗口、分子用整屏且不加回窗口偏移，导致只要窗口不全屏就系统性偏移。
2. **单窗口截图比全屏截图好算得多**：比例就是 `窗口逻辑宽 / 图宽`，不用管屏幕缩放、
   菜单栏偏移、多显示器排列。
3. `screencapture -R x,y,w,h` **吃逻辑点、吐物理像素**，man page 一个字都没写。
   `CGDisplayPixelsWide` 也不返回像素，返回的是逻辑点。要真实缩放比用 `backingScaleFactor`。
4. **NSEvent 与 CGEvent 的 Y 轴相反**（`cg_y = 屏高 - ns_y`）。混用时的症状是
   「水平完全对、垂直镜像」，容易被误判成偏移。

要把坐标存进 `app档案.md`，**一律存归一化坐标（至少 4 位小数）+ 锚点描述 + 实测窗口尺寸**——
1% 的量化误差在 1440 点宽的屏幕上就是 ±14 点，足以点偏一个按钮；
只有绝对像素对而没有锚点描述，下次截了图也无从判断「对不上」。

## 输入路径：三条能写中文的路，一条不能

| 路径 | 抢焦点 | 可靠性 | 备注 |
|---|---|---|---|
| app 自己的字典命令（L0） | 否 | **最高** | 完全不碰事件系统 |
| `mac axset`（AX setValue） | 否 | 高（原生控件、`<input>`/`<textarea>`） | **contenteditable 常失效** |
| `mac type <pid> <文本> global`（CGEvent 投 Unicode） | 是（窗口需已激活） | 高 | 在一个 Electron 客户端上实测有效 |
| 剪贴板 + `mac key <pid> 9 cmd`（Cmd+V） | 是 | 中 | **破坏用户剪贴板**，且还原不了图片和富文本 |
| `osascript ... keystroke "中文"` | 是 | 🔴 **禁用** | 静默变成 `aaaa` |

🔴 **`keystroke` 打非 ASCII 会静默降级**：`keystroke "ABC-中文测试-DEF"` 读回是 `ABC-aaaa-DEF`，
不报错、不警告、退出码 0。原因是它走虚拟键码路径映射到当前布局，非 ASCII 没有对应键位。
**这比「打不出来」危险得多**——会在搜索框搜 `aaaa`、在表单提交 `aaaa`、在聊天窗口发出 `aaaa`。
另外 `keystroke` 是**追加语义**、天然不幂等，重跑一次读回是两份内容；用 `setValue` 绝对赋值代替。

`mac type` 的实现要点（已在内核里）：`virtualKey` 传 0，字符内容全由
`keyboardSetUnicodeString` 承载，绕开键盘布局；utf16 数组天然处理 emoji 的代理对；
分块之间留 12 毫秒，太快会丢字符。

## `postToPid` 后台投递：机会性优化，不是主路径

`mac click ... bg` 和 `mac type`（不带 `global`）走的是 `CGEventPostToPid`。
理论上能给后台进程发键鼠、不抢焦点，实际有四种失败模式，只有第一种能修：

| # | 失败模式 | 能不能修 |
|---|---|---|
| 1 | **发送端 post 完立刻退出，事件在 flush 前连接就被拆了** | ✅ post 完 sleep ≥1 毫秒（内核留了 300 毫秒） |
| 2 | 模态循环饿死（模态 run-loop 丢弃非活动 app 的事件） | ❌ |
| 3 | 目标用全局热键 / 裸 HID 监听——头文件明写 postToPid「在任何 event tap 之前投递」，**按设计绕过全局流** | ❌ 永久无解 |
| 4 | Chromium 非激活时 `keyWindow == nil`，`[nil sendEvent:]` 静默 no-op | ❌ |

第 1 条在任何公开资料里都没人写过，它很可能解释了社区里绝大多数「it silently does nothing」——
那些几乎都来自一次性 CLI 和短命脚本，长驻进程（Hammerspoon 之类）从来没人抱怨过。

**但修好第 1 条之后仍可能不接受**：豆包工作实测加满 300 毫秒投递窗口、等满 10 秒复测，
仍然完全无效。所以两条硬性要求：**留够投递窗口；必须读回验证。主路径仍是借焦点 + 全局流。**

两条要破除的 cargo cult：
- **`CGEventSource` 的 stateID 完全无所谓**：Private / Combined / HID / 甚至 NULL source 都能投递成功。
  「必须用 HIDSystemState」在 macOS 26 上是迷信。
- **API 没有错误通道**：`CGEventPostToPid` 返回 void，它无法告诉你失败了。

另注：macOS 26 加了一层新过滤——`CGEventPost` 合成的**带修饰键**事件到不了 Carbon 热键监听器
（裸按键可以）。症状是完全静默。

## 等 UI 就绪

**通用模式：轮询 + 超时 + 明确的失败**，不要固定 sleep。轮询循环自己写，只有一条不是常识：
**等窗口出现要轮询 `mac windows`，不要用 System Events**——前者跨 Space 可靠，后者会返回 0。

- AppleScript 里 `with timeout of 10 seconds` **必须显式写**，默认 120 秒且很多阻塞场景根本不触发。
- **等「加载中」消失比等「内容出现」更可靠**——很多 app 先渲染控件再填数据。
- 像素差异轮询是 AX 不可用时的兜底：连拍同一窗口比对，连续 3 帧稳定视为就绪。
  ⚠️ 哈希法对**有光标闪烁、有动画、有时钟**的界面永远不会稳定，改成比缩略图均值差或排除变化区域。
- **模态 sheet 会让目标 app 的 Apple Events 处理停摆**，表现为 osascript 卡到 `-1712`。
  操作前先探 `exists sheet 1 of window 1`。

> 同一段代码失败一次、成功两次的实录：第一次跑全局 CGEvent 输入读回空字符串，换个 tap 重跑成功，
> 再用**原来那个 tap** 重跑也成功，代码一字未改。差异来自时序——清空文档后目标文本区还没真正
> 拿到键盘焦点，0.5 秒的 sleep 不够。**这就是为什么「固定 sleep + 假定成功」的自动化必然不可靠。**

## 性能：瓶颈不在截图

全屏截图 0.10 秒、单窗口 0.15 秒、osascript 往返 0.17 秒。**瓶颈从来是模型往返**，
优化方向是「少截几张、一次做完多步」，不是压缩截图耗时。
要降采样给模型看，同样走 image-compress，不要现写 sips 循环。
